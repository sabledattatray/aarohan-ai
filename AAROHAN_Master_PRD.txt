# PROJECT AAROHAN AI
## Product Requirements Document (PRD)
### Version 1.0 | November 2026
**Project Type:** Independent Foundation Language Model & Autonomous Continual-Learning AI  
**Development Philosophy:** Research-driven, open-source, free-resource-first  
**Primary Objective:** Build an original AI model with its own neural network architecture, training pipeline, persistent memory, autonomous knowledge acquisition and controlled self-improvement capabilities.

---

# 1. EXECUTIVE SUMMARY

## 1.1 Product Vision

AAROHAN AI is an independently developed artificial intelligence research project designed to create a continuously improving language model.

Unlike conventional chatbot applications that rely entirely on an external AI provider, AAROHAN will have its own trainable neural network, tokenizer, model weights, datasets, training infrastructure, evaluation framework and knowledge architecture.

The system must progressively acquire language capabilities, understand patterns, generate responses, retain useful information, learn from curated new knowledge, evaluate its own performance and improve through controlled training cycles.

The long-term objective is to evolve AAROHAN into an increasingly capable autonomous learning system.

## 1.2 Core Product Principles

1. Independent model ownership: All core model architecture, tokenizer, weights and training pipelines must belong to the project.
2. No mandatory paid AI APIs: The core system must operate without OpenAI, Gemini, Claude or other paid inference services.
3. Open-source first: Use free and permissively licensed tools, libraries, datasets and research resources.
4. Persistent memory: Knowledge and experiences must survive application restarts and model upgrades.
5. Continuous learning: The system must have a repeatable mechanism for learning from new, verified information.
6. Measurable intelligence: Improvements must be demonstrated through benchmark results rather than subjective claims.
7. No uncontrolled self-modification: Every model update must pass testing, evaluation and rollback procedures.
8. Modular architecture: Components must be independently replaceable and scalable.
9. Reproducibility: Every training run must be documented, versioned and reproducible.
10. Long-term independence: The system must not depend on an external commercial model for its fundamental intelligence.

## 1.3 Definition of Success

AAROHAN will be considered a successful initial research product when it can:

- Run its own independently trained language model.
- Generate coherent responses without calling external AI APIs.
- Process and understand new documents.
- Store and retrieve information using persistent memory.
- Recognize knowledge gaps.
- Propose and execute approved learning tasks.
- Evaluate answers against trusted references.
- Learn new information through controlled training.
- Retain previously learned capabilities after new training.
- Demonstrate measurable improvements across repeated evaluation cycles.

The system must distinguish between remembering information, retrieving information and actually modifying model parameters through training.

# 3. SYSTEM ARCHITECTURE

AAROHAN must be developed as a combination of an original language model and an external cognitive architecture.

The neural model provides learned language capabilities. Memory, retrieval, planning, research and evaluation provide additional capabilities around the model.

## 3.1 High-Level Architecture

```text
                  AAROHAN AI
                       |
             CENTRAL ORCHESTRATOR
                       |
       +---------------+----------------+
       |               |                |
   AI MODEL       MEMORY SYSTEM     LEARNING ENGINE
       |               |                |
  Transformer       Short-term       Knowledge Gap
  Neural Network    Episodic          Detection
  Tokenizer         Semantic          Research Planner
  Embeddings        Knowledge         Learning Queue
       |            Memory            Training Samples
       |               |                |
       +---------------+----------------+
                       |
                RESEARCH ENGINE
                       |
             Approved Information Sources
                       |
              DOCUMENT PROCESSING
                       |
              KNOWLEDGE VALIDATION
                       |
                EVALUATION ENGINE
                       |
              CONTINUAL LEARNING
                       |
                TRAINING PIPELINE
                       |
              NEW MODEL CHECKPOINT
                       |
                REGRESSION TESTS
                       |
               MODEL REGISTRY
                       |
               PRODUCTION MODEL
```

## 3.2 Architectural Separation

The following boundaries are mandatory:

**Neural model:** Learns statistical representations and language patterns through training.

**Memory system:** Stores facts, conversations, experiences, source references and learned preferences.

**Knowledge system:** Stores structured, sourced information and relationships.

**Research system:** Finds and proposes new learning material.

**Learning engine:** Converts validated information and feedback into training candidates.

**Training engine:** Updates model parameters through controlled optimization.

**Evaluation engine:** Measures whether updates improve performance without damaging existing capabilities.

No single component should be responsible for all these operations.

# 4. ORIGINAL FOUNDATION MODEL

## 4.1 Model Identity

Model name: AAROHAN-1

Architecture: Decoder-only Transformer.

Training method: Autoregressive next-token prediction.

Initialization: Randomly initialized weights.

Implementation framework: PyTorch.

Tokenizer: Project-owned Byte Pair Encoding (BPE) tokenizer.

Inference: Local Python inference engine.

The first model must be genuinely trained from random initialization. Loading an existing pretrained model and renaming it is not acceptable as the foundation-model implementation.

## 4.2 Model Development Strategy

We will use a progressive model development strategy.

| Version | Target parameters | Purpose |
|---|---:|---|
| AAROHAN-0.01 | 5M–10M | Architecture validation |
| AAROHAN-0.10 | 25M–50M | Language-model research |
| AAROHAN-0.50 | 100M–150M | Improved language capability |
| AAROHAN-1.0 | 300M–500M | Initial foundation-model target |
| AAROHAN-2.0 | 1B+ | Future expansion, hardware permitting |

These are engineering targets, not guaranteed performance milestones. The project must select model size according to measured hardware capability and available training tokens.

A smaller, adequately trained model is preferable to a larger, severely undertrained model.

## 4.3 Initial Model Configuration

The following is the proposed starting configuration for the architecture, subject to benchmarking.

| Parameter | Initial configuration |
|---|---|
| Architecture | Decoder-only Transformer |
| Vocabulary | 16,000–32,000 tokens |
| Context length | 1,024 tokens initially |
| Transformer blocks | 8 |
| Attention heads | 8 |
| Hidden dimension | 512 |
| Feed-forward dimension | 2,048 |
| Normalization | RMSNorm |
| Activation | SwiGLU |
| Positional encoding | RoPE |
| Attention | Causal self-attention |
| Output | Vocabulary logits |
| Loss | Cross-entropy |
| Optimizer | AdamW |
| Initialization | Random |
| Training precision | FP32 initially, BF16/FP16 when supported |

The configuration must be validated by a parameter-counting test, forward-pass test, backward-pass test and memory benchmark.

## 4.4 Required Model Components

### A. Token Embeddings

Convert token IDs into numerical representations.

### B. Positional Encoding

Implement rotary positional embeddings to provide token-position information.

### C. Causal Self-Attention

Each token must attend to permitted preceding tokens, never future tokens during autoregressive training.

### D. Feed-Forward Network

Implement gated feed-forward layers using SwiGLU.

### E. Residual Connections

Preserve information flow through deep Transformer layers.

### F. Normalization

Use RMSNorm to stabilize training.

### G. Language Modeling Head

Project hidden representations into vocabulary logits.

### H. Autoregressive Generation

Implement greedy, temperature, top-k and top-p decoding.

## 4.5 Training Objective

The initial foundation model must learn to predict the next token.

For a token sequence:

`[I, am, learning, artificial, intelligence]`

The model learns to predict:

- I → am
- I am → learning
- I am learning → artificial
- I am learning artificial → intelligence

Training objective:

Minimize next-token cross-entropy loss.

The model must use teacher forcing during training and autoregressive generation during inference.

# 8. INSTRUCTION TUNING AND ALIGNMENT

Pretraining teaches language patterns. It does not automatically produce a reliable conversational assistant.

AAROHAN requires post-training.

## 8.1 Supervised Fine-Tuning (SFT)

Develop a high-quality instruction dataset containing:

- Questions and answers.
- Explanations.
- Summarization.
- Reasoning examples.
- Coding assistance.
- Educational conversations.
- Refusal examples.
- Structured output.
- Multi-turn conversations.

Train using assistant-response targets while masking loss on non-target tokens where appropriate.

## 8.2 Preference Optimization

Future versions should support Direct Preference Optimization (DPO).

Requirements:

- Collect human-reviewed preference pairs.
- Identify preferred and rejected answers.
- Validate data quality.
- Train a preference-optimized model.
- Compare results with the original SFT checkpoint.

## 8.3 Human Feedback

Build a feedback interface with:

- Helpful.
- Not helpful.
- Incorrect.
- Incomplete.
- Unsafe.
- Needs source.
- Better answer suggestion.

Feedback must be stored independently.

A negative rating must never automatically change model weights.

## 8.4 Alignment Requirements

The model must learn to:

- Acknowledge uncertainty.
- Avoid fabricated citations.
- Refuse clearly harmful requests.
- Separate facts from assumptions.
- Respect user privacy.
- Identify outdated information.
- Explain limitations.
- Ask clarifying questions when necessary.

RLHF is a possible future research direction. It requires a carefully designed feedback and reward-training pipeline, not merely a thumbs-up button.

# 9. AAROHAN MEMORY ARCHITECTURE

This is one of the highest-priority modules.

The system must not rely on the model's context window as its only memory.

Memory must exist independently of model parameters and survive model replacement.

## 9.1 Memory Layers

### Layer 1 – Working Memory

Stores current conversation context, task state and temporary reasoning information.

### Layer 2 – Episodic Memory

Stores significant events and previous interactions.

Example:

AAROHAN previously attempted a mathematical problem, generated an incorrect result, received verified feedback and stored the correction.

### Layer 3 – Semantic Memory

Stores facts, concepts, definitions and relationships.

Example:

Transformer → Neural Network Architecture → Self-Attention.

### Layer 4 – Procedural Memory

Stores successful procedures and reusable workflows.

Example:

How to execute a verified data-cleaning workflow.

### Layer 5 – Knowledge Graph

Stores entities and relationships between concepts.

Example:

Python → Programming Language → Used in → Machine Learning.

### Layer 6 – Learning Memory

Stores:

- Previous training experiences.
- Evaluation failures.
- Knowledge gaps.
- Successful learning strategies.
- Model versions.
- Training history.
- Regression results.

## 9.2 Memory Technology

- PostgreSQL: Persistent structured storage.
- pgvector: Vector similarity search.
- Full-text search: Keyword retrieval.
- Redis: Optional temporary cache; PostgreSQL must remain sufficient without it.
- Object storage: Local files and datasets.
- Graph relationships: PostgreSQL relational tables initially, dedicated graph technology only when justified.

## 9.3 Memory Record Structure

Each memory should contain:

- Unique memory ID.
- Memory type.
- Content.
- Source.
- Creation timestamp.
- Last accessed timestamp.
- Confidence score.
- Verification status.
- Importance.
- Recency.
- Privacy classification.
- Embedding.
- Related memory IDs.
- Expiration policy.
- Version information.

## 9.4 Memory Lifecycle

```text
NEW INFORMATION
      |
EXTRACTION
      |
CLASSIFICATION
      |
DUPLICATE CHECK
      |
SOURCE VALIDATION
      |
CONFIDENCE ASSESSMENT
      |
MEMORY STORAGE
      |
RELATIONSHIP CREATION
      |
RETRIEVAL WHEN NEEDED
      |
REINFORCEMENT / CORRECTION
      |
ARCHIVING OR EXPIRATION
```

## 9.5 Memory Quality Rules

- Never treat every conversation statement as a verified fact.
- Keep user claims separate from independently verified facts.
- Preserve source references.
- Allow corrections.
- Detect contradictory memories.
- Record uncertainty.
- Support memory deletion.
- Prevent unauthorized access to private information.
- Never use confidential user information for general model training without explicit authorization.

## 9.6 Memory Consolidation

Implement scheduled memory consolidation.

The system should:

1. Review recent episodic records.
2. Identify recurring concepts.
3. Detect duplicates.
4. Extract stable knowledge.
5. Link related records.
6. Resolve contradictions where evidence allows.
7. Preserve original source references.
8. Generate candidate semantic memories.
9. Submit uncertain records for review.

Memory consolidation must not silently convert an uncertain claim into a verified fact.

# 10. AUTONOMOUS LEARNING ENGINE

## 10.1 Core Objective

AAROHAN must progressively identify what it does not know and organize opportunities to improve.

It must not merely wait for a human to supply every training document.

## 10.2 Knowledge Gap Detection

The system should identify gaps through:

- Failed evaluation questions.
- Unanswered user questions.
- Repeated low-confidence responses.
- Missing knowledge graph relationships.
- Outdated knowledge records.
- Unsuccessful tasks.
- Human feedback.
- Benchmark weaknesses.

## 10.3 Learning Planner

For each knowledge gap, generate a learning task containing:

- Topic.
- Reason for learning.
- Expected learning outcome.
- Required sources.
- Source quality requirements.
- Risk classification.
- Estimated complexity.
- Evaluation method.
- Completion status.

## 10.4 Independent Research

The research engine should be able to:

- Search approved public information sources.
- Retrieve documentation.
- Read downloaded documents.
- Extract important concepts.
- Compare multiple sources.
- Identify conflicting statements.
- Produce source-linked summaries.
- Propose structured knowledge records.

Research must be bounded by source permissions, rate limits and resource budgets.

## 10.5 Learning Verification

Before new knowledge enters the trusted knowledge base:

- Check source provenance.
- Compare independent references where possible.
- Identify publication dates.
- Detect contradictions.
- Run factual consistency checks.
- Store confidence and evidence.
- Require human review for high-risk or uncertain claims.

The model must not be allowed to validate its own generated answer as ground truth without independent evidence.

# 11. CONTINUAL LEARNING AND MODEL SELF-IMPROVEMENT

This section is the defining research component of AAROHAN.

## 11.1 The Difference Between Memory and Learning

Memory:

AAROHAN stores a new fact in PostgreSQL and retrieves it later.

Model learning:

AAROHAN uses a curated training example to update neural-network parameters through gradient-based optimization.

These are different operations and must be reported separately in the system dashboard.

## 11.2 Controlled Continual-Learning Loop

```text
OBSERVE NEW INFORMATION
          |
IDENTIFY KNOWLEDGE GAP
          |
CREATE LEARNING TASK
          |
COLLECT APPROVED SOURCES
          |
VALIDATE INFORMATION
          |
GENERATE TRAINING CANDIDATES
          |
HUMAN / AUTOMATED REVIEW
          |
CREATE VERSIONED DATASET
          |
REPLAY OLD TRAINING EXAMPLES
          |
TRAIN CANDIDATE MODEL
          |
RUN REGRESSION BENCHMARKS
          |
COMPARE AGAINST CURRENT MODEL
          |
       PASS?
       /   \
     YES    NO
      |      |
  STAGING  REJECT
      |
  APPROVAL
      |
  DEPLOY NEW MODEL
      |
  MONITOR PERFORMANCE
      |
  RETAIN ROLLBACK CHECKPOINT
```

## 11.3 Catastrophic Forgetting Prevention

AAROHAN must not lose old capabilities whenever it learns something new.

Implement:

**Experience Replay:** Preserve a representative sample of previous training examples and mix them into new training runs.

**Replay Sampling:** Maintain balanced sampling across domains.

**Regularization:** Experiment with methods such as Elastic Weight Consolidation where practical.

**Evaluation Gates:** Re-run historical benchmarks after each update.

**Adapter-Based Experiments:** Test parameter-efficient adapters before modifying the primary model.

**Model Rollback:** Restore the previous stable checkpoint if regression thresholds are violated.

## 11.4 Learning From Mistakes

When an error is detected:

1. Store the original question.
2. Store the original answer.
3. Record the verified correction.
4. Record the evidence.
5. Classify the error.
6. Identify whether the failure was knowledge-related, reasoning-related or retrieval-related.
7. Create a candidate learning example.
8. Add the example to the appropriate review queue.
9. Test the updated system.
10. Measure whether the failure rate improves.

Do not automatically train on every conversation or every generated answer. That creates feedback loops and can reinforce hallucinations.

## 11.5 Self-Improvement Metrics

Track:

- Validation loss.
- Perplexity.
- Domain accuracy.
- Factual accuracy.
- Instruction-following accuracy.
- Retrieval precision.
- Retrieval recall.
- Memory consistency.
- Hallucination rate on controlled tests.
- Regression rate.
- Learning-task success rate.
- Training cost.
- Tokens processed.
- Model size.
- Checkpoint stability.

Every claimed improvement must be backed by a reproducible evaluation.

# 18. SECURITY AND RESPONSIBLE LEARNING

Autonomous learning creates risks that must be addressed from the beginning.

## 18.1 Threats

- Prompt injection inside documents.
- Malicious training samples.
- Poisoned knowledge sources.
- Data exfiltration.
- Private information leakage.
- Model memorization.
- Unsafe autonomous actions.
- Training data contamination.
- Self-reinforcing incorrect answers.

## 18.2 Mandatory Controls

- Treat all external documents as untrusted input.
- Never execute instructions found inside ingested documents.
- Separate model-generated text from verified evidence.
- Sandbox all code execution.
- Disable unrestricted shell access.
- Enforce source allowlists where appropriate.
- Record every autonomous action.
- Require explicit approval for sensitive operations.
- Maintain model and dataset rollback.
- Support user data deletion.
- Apply privacy filters before training.
- Never expose internal credentials to the model.

## 18.3 Learning Safety

AAROHAN must not use its own generated responses as unquestioned training truth.

Training data must be sourced, reviewed or validated using independent evaluation procedures.
